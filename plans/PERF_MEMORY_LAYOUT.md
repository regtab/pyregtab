# План: раскладка памяти на крупных таблицах (0.7.2, второй раунд)

**Статус:** В РАБОТЕ (2026-09-08)
**Дата:** 2026-09-08
**Предшественник:** [PERF_LARGE_TABLES.md](PERF_LARGE_TABLES.md) — после него pyRegTab 0.7.2
на `stack_test11` (1,19 млн ячеек) занимает 531 МБ пика против 125 МБ у pandas и 2210 МБ у
jRegTab; по времени 1,12 с против 1,24 с у pandas (wall). Вопрос пользователя: можно ли
снизить RSS без ущерба скорости вычислений.
**Характер:** только раскладка памяти в ядре. Семантика RTL, паритет с jRegTab 0.7.1,
публичный Python-API и контракт CLI-раннера не меняются. Та же ветка и версия 0.7.2.

## 1. Раскладка пика (оценка, `stack_test11`: 1,19 млн ячеек = элементов = записей, 2,38 млн действий)

| слой | байт на единицу | МБ | примечание |
|---|---|---|---|
| строки ячеек (`Arc<str>`) | ~48 (заголовок 16 + данные + гранулярность heap) | ~57 | 1,19 млн мелких аллокаций; разделяются с элементами и записями |
| `CellData` | 56 | 67 | `row`, `col`, `Text`, флаги, `Option<Box<CellFormat>>` |
| `CellItem` | 88 | 105 | `Text`, `Vec` тегов, `index`/`row`/`col` usize, `span` |
| `ActionInst` | 24 | 57 | `ItemId` 16 + `Arc` |
| `ItemIndex` | 16 | 19 | два порядка `usize` |
| `WorkingState.val`/`attr` | 16 + 16 | 38 | плотные `Option<Text>`, `attr` почти пуст |
| `WorkingState.avp` | 24 | 29 | `(u32, Text)`; значение всегда равно `val(item)` |
| `WorkingState.rec` | 32 слот + 48 heap | 95 | `Records` + `Vec<ItemId>` на каждую запись |
| записи | 24 + 48 heap | 86 | `RecordCore { Vec<Option<Text>> }` на запись |
| транзиенты | | ~65 | тройки `visit_order` 28, `live_anchors` ×2 19, группы действий `Vec<&ActionInst>` 19 |

Пик достигается в `generate_records`, когда живы таблица, семантика, рабочее состояние и
записи одновременно; раньше освободить ничего нельзя (объекты живут в Python).

## 2. Шаги (каждый — замер до/после, полный набор проверок §2 предыдущего плана)

1. **Аллокатор mimalloc** для расширения (feature `python`; чистое ядро для rtl-lsp — без
   глобального аллокатора, чтобы не конфликтовать с хостом). Ожидание: меньше накладных
   расходов на объект и быстрее фазы с миллионами аллокаций.
2. **Рабочее состояние**: `rec` — одна арена `Vec<ItemId>` + `(start, len)` на якорь вместо
   `Vec` на запись; `avp` — только id атрибута (значение = `val(item)`, инвариант: все
   строковые операции применяются до `AVP`, `set_avp` всегда получает `val(item)`);
   `val`/`attr` — только переопределения поверх `item.s` (без фазы инициализации).
   Транзиенты: `visit_order` — итератор, `live_anchors` — один раз, группы действий —
   индексы `u32`.
3. **Плоский recordset**: `RecordsetCore { schema, values: Vec<Option<Text>> }` со страйдом =
   число атрибутов; `RecordCore` исчезает из ядра (Python-типы `Record`/`Recordset` не
   меняются).
4. **Упаковка в u32** (если 1–3 не дадут ≤ 350 МБ): `ItemId` 8 байт, `CellItem` ~48 байт,
   `CellData` без `row`/`col`.

Цель: пик RSS `stack_test11` ≤ 350 МБ при k = 1 (и ≤ 1,4 ГБ при k = 4) без замедления
`match`/`transform` (допуск ±5 %).

## 3. Журнал

### 3.1. mimalloc — СДЕЛАНО

`mimalloc = { version = "0.1", default-features = false, optional = true }`, включается
фичей `python` (`#[global_allocator]` в `lib.rs` под `cfg(feature = "python")`). Сборка
требует C-компилятор (на этой машине — `C:/Users/1/mingw64/bin/gcc.exe`, не в PATH по
умолчанию; в CI на MSVC берётся `cl.exe`).

| кейс | wall | read | match | transform | write | RSS |
|---|---|---|---|---|---|---|
| `stack_test11` | 1,11 → **0,93** с | 0,134 → 0,086 | 0,223 → 0,202 | 0,543 → 0,457 | 0,044 → 0,041 | 523 → **484** МБ |
| `explode_test22` | 0,29 → **0,26** с | 0,035 → 0,026 | 0,059 → 0,047 | 0,091 → 0,090 | — | 122 → **117** МБ |
| `stack_test11` k = 4 | 4,46 → **3,65** с | 0,532 → 0,332 | 0,907 → 0,811 | 2,396 → 2,000 | 0,185 → 0,166 | 2065 → **1903** МБ |

Проверки: pytest 2013, cargo test 49+49, clippy 0, differential 750/750, bytecmp 244/244.

### 3.2. Рабочее состояние — СДЕЛАНО

- `rec`: одна арена `items: Vec<ItemId>`, на якорь `RecEntry::One { start, len }` (8 байт)
  или `Many(Box<[(u32, u32)]>)` после `JOIN`; `rec(anchor)` возвращает `RecordsRef` (len/get/
  iter/to_vec). Ни одной аллокации на запись в `O_rec`.
- `avp: ItemMap<u32>` — только id атрибута; значение всегда `val(item)` (инвариант описан в
  документации `WorkingState`: все строковые операции применяются до `AVP`, `set_avp`
  вызывается только при наличии `val`). `key_mismatch`/`agree`/диагностика берут значение
  через `val`.
- `val`/`attr` — карты переопределений (`val_over`/`attr_over`) поверх `item.s` по типу
  элемента; фаза инициализации рабочего состояния исчезла. Все обращения — `ws.val(sem, ι)`,
  `ws.attr(sem, ι)`.
- Транзиенты: группы действий — `Vec<u32>` индексов; `visit_schema` обходит тройки без
  материализации; `live_anchors` вычисляется один раз на извлечение.

| кейс | wall | match | transform | RSS |
|---|---|---|---|---|
| `stack_test11` | 0,93 → **0,84** с | 0,202 → 0,201 | 0,457 → 0,373 | 484 → **429** МБ |
| `explode_test22` | 0,26 → **0,24** с | 0,047 → 0,048 | 0,090 → 0,071 | 117 → **107** МБ |
| `stack_test11` k = 4 | 3,65 → **3,39** с | 0,811 → 0,838 | 2,000 → 1,700 | 1903 → **1680** МБ |

Проверки: pytest 2013, cargo test 49+49, clippy 0, differential 750/750, bytecmp 244/244.

### 3.3. Плоский recordset — СДЕЛАНО

`RecordsetCore { schema, width, len, values: Vec<Option<Text>> }` — все значения в одном
векторе со страйдом = число атрибутов; `record(i)`/`record_mut(i)`/`records()`/`push`/
`push_slice`/`from_rows`/`map_values`. `RecordCore` удалён; трансформации (`spec.rs`) и
биндинги (`Record`, `Recordset`, `to_pandas`, `to_csv`) переписаны на срезы. Python-API без
изменений.

| кейс | wall | transform | RSS |
|---|---|---|---|
| `stack_test11` | 0,84 → **0,83** с | 0,373 → 0,355 | 429 → **395** МБ |
| `explode_test22` | 0,24 → **0,23** с | 0,071 → 0,064 | 107 → **96** МБ |
| `stack_test11` k = 4 | 3,39 → **3,27** с | 1,700 → 1,654 | 1680 → **1672** МБ |

Проверки: pytest 2013, cargo test 49+49, clippy 0, differential 750/750, bytecmp 244/244.

Оценка раскладки при k = 4 (4,75 млн ячеек) теперь сходится с измерением: ячейки
4,75 млн × (56 + ~40 строка) ≈ 456 МБ, элементы × 88 ≈ 418 МБ, действия 9,5 млн × 24 ≈ 228 МБ,
индекс 76, рабочее состояние ≈ 340, записи 152 — итого ≈ 1670 МБ. Дальше — только упаковка
(шаг 4).

### 3.4. Упаковка — СДЕЛАНО

- `CellData` 56 → 32 байта: без `row`/`col` (позиция известна вызывающему —
  `format(row, col)`/`format_mut(row, col)`), `text_indent: u32`.
- `ActionInst` 24 → 16: якорь упакован в `u32` (`ItemId::pack`/`unpack`, старший бит —
  контекстный элемент), доступ через `anchor()`.
- `RecEntry` 24 → 12: `Many { first, count }` — диапазоны в побочной таблице
  `WorkingState.ranges`.
- `ItemIndex`: порядки `Vec<u32>`, `Range.items: &[u32]` (19 → 9,5 МБ на миллион элементов).
- `CellItem` 88 → 72: `index: u32`, `span: (u32, u32)` (Python-тип `CellDerivedItem`
  по-прежнему отдаёт `int`/`tuple[int, int]`).
- `CellPredicate::test(cell, (row, col), env)` — позиция передаётся явно (нужна только
  внешним/пользовательским предикатам).
- `ItemId` (16 байт) и `CellItem.row`/`col` (`usize`) не трогались: 97 и ~60 мест правок,
  выигрыш ещё ≈ 50 МБ на миллион ячеек — оставлено как резерв.

| кейс | wall | match | transform | RSS |
|---|---|---|---|---|
| `stack_test11` | 0,83 → **0,76** с | 0,201 → 0,179 | 0,355 → 0,319 | 395 → **317** МБ |
| `explode_test22` | 0,23 → **0,23** с | 0,048 → 0,043 | 0,064 → 0,057 | 96 → **82** МБ |
| `stack_test11` k = 4 | 3,27 → **2,94** с | 0,826 → 0,721 | 1,654 → 1,444 | 1672 → **1255** МБ |

Проверки: pytest 2013, cargo test 49+49, clippy 0, differential 750/750, bytecmp 244/244.
